当多个 Agent 或应用需要共享同一个 workspace，且不应在自身进程中管理 ReMe 时，可以将 ReMe 作为独立服务运行。服务负责持久化、索引、定时整合以及配置的 job。

## 选择接口

MCP、CLI 和 HTTP 访问同一个 ReMe workspace 与 job。请选择宿主已经支持的调用边界：

| 接口 | 适用场景 | 调用边界 |
|---|---|---|
| MCP | 带有 MCP client 的 Agent 或应用 | 通过共享 MCP 端点发现并调用工具 |
| CLI | 可以执行 shell 命令的 Agent 与自动化任务 | 向运行中的 ReMe 服务发送命令 |
| HTTP | 跨语言应用、自定义 client 和 ReMe Studio | 访问 job 端点和可选 Web UI |

MCP 和 HTTP 是服务协议；CLI 是运行中服务的客户端，通常最适合能够执行 shell 命令的 Agent。

## 服务生命周期

一个 workspace 只保留一个运行时所有者。启动一个共享服务，让所有 client 连接该服务；不要再针对同一个 workspace 启动第二个进程内 `ReMe` 应用。

服务负责后台索引和定时整合；宿主仍需负责会话 hook、稳定的 session ID，以及何时召回或记录记忆。

## MCP

以 MCP backend 启动 ReMe：

```bash
reme start service.backend=mcp service.transport=streamable-http
```

默认端点为 `http://127.0.0.1:2333/mcp`。将该 URL 添加到 MCP client 后，客户端会发现当前 ReMe 版本公开的工具。修改端口时，服务端和客户端必须保持一致。

MCP 允许模型选择工具；会话自动记录仍应由宿主的 hook 或生命周期负责。

## CLI

先启动服务，再通过普通的 `reme <action>` 命令调用它：

```bash
reme start

reme search query="项目决策" limit=5
reme read path=digest/wiki/project-decisions.md
reme auto_memory \
  session_id="conversation-42" \
  messages='[{"role":"user","content":"记住每周五发布版本。"}]'
```

CLI 会检测正在运行的服务配置，也能连接 MCP backend。排查 client 行为前，可以先运行 `reme find_reme` 和 `reme health_check`。

## HTTP

默认启动方式会公开 HTTP 服务：

```bash
reme start
```

当 Web 构建可用时，同一地址的 `/` 还会提供 ReMe Studio。Studio 可以浏览、编辑和搜索 workspace，与只读 workspace agent 进行流式对话，并可视化 digest wikilink 图。通过 `service.web_enabled=false` 可以关闭；也可使用 `service.web_static_dir` / `REME_WEB_STATIC_DIR` 指定自定义构建。找不到 Web 产物不会阻止 Job API 启动。

每个已公开 job 对应 `POST /{action}`，请求体使用 JSON：

```bash
curl -s http://127.0.0.1:2333/search \
  -H 'Content-Type: application/json' \
  -d '{"query":"项目决策","limit":5}'
```

服务运行后，可通过 `/docs` 或 `/openapi.json` 获取与当前安装版本一致的 schema。不要在 client 代码中复制固定的旧参数表。

<Note>
HTTP 通过 server-sent events 暴露 `chat` 等流式 job；MCP 当前会跳过流式 job 和后台 job。
</Note>
